# Explain one command from Rust source

Input: exact case-sensitive command ID and optional source checkout. If no ID was supplied, ask for it. Output: `docs/commands/cmd-<encoded-id>.md` plus updates to both indexes and a scoped scan report.

Read [the shared contract](../../../workflows/source-documentation.md), [command detail template](../../../templates/command-detail.md), [command index template](../../../templates/command-index.md), [tool index template](../../../templates/tool-index.md), and [scan report template](../../../templates/scan-report.md).

1. Read both existing indexes and the existing detail page. Resolve the exact ID in current source, not just its index entry. Search exports, registrations, aliases, shell handlers, and catalog tables. If the ID is absent, report that with nearby verified IDs without silently substituting one. Preserve any historical page. For catalog-only IDs, document the absence of implementation rather than fabricate a core flow.
2. Trace registration → enabled/admission checks → actual caller/shell interception → run handler → important lower-layer helpers → mutation/result/history. Include material error branches, asynchronous completion/cancel paths, preview versus commit, and differences between UI and headless invocation. Follow abstractions until the actual behavior is explained; a list of function names is insufficient.
3. Extract the actual core Rust code: relevant registration/run closure, validation and branching, central algorithm, and data structures. Include enums/struct fields/type aliases that explain the data flow, ownership, and state changes. Place each excerpt beside an explanation of what enters, what changes, and what returns. Cite file, symbol, lines, and source revision for each excerpt. Use separate code blocks for noncontiguous ranges; label omitted ranges outside blocks. Keep quoted Rust verbatim. Clearly label any explanatory pseudocode, never present it as source. Do not paste entire large files or silently simplify code inside a quoted excerpt.
4. Fill Purpose, Context to use, Inputs/results, Core logic flow, and Structures used from the template, plus caller links, errors, history/effects, tests, and limitations. Explain selection, active layer/mask, color mode/depth, locks, and platform behavior where the actual implementation depends on them. Trace checks independently of the UI enabled predicate: automation may enter differently. Use a compact flow diagram only when it clarifies real branching.
5. Include an invocation example validated against the handler's actual input parsing. State required context and the real dispatch surface; shell-only commands may require the running UI. Do not execute a mutation merely to produce the example. Label tests as inspected or executed, with the command/result if executed. Distinguish source-supported facts from inference and unresolved details.
6. Create missing indexes using their templates with explicitly partial coverage. Update the command record and every verified caller tool record, adding both command-index and detail-page links. Existing stale bindings must be reconciled within this command's scope on both sides; do not delete unrelated unseen records. Add backlinks from the detail page to the command record and specific tools. Preserve Notes, first-seen metadata, and history. Mark the refreshed detail CURRENT with the verified source revision, or record incomplete sections explicitly.
7. Write the scoped scan report and validate links/anchors, reciprocal bindings, excerpt accuracy, and unresolved template tokens. Report the detail-page link, which indexes changed, and any gaps. A one-command documentation run is not a complete inventory scan.
