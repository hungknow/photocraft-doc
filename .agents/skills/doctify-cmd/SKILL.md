# Explain one command from Rust source

Input: exact case-sensitive command ID and optional source checkout. If no ID was supplied, ask for it. Output: `docs/commands/<category-slug>/cmd-<encoded-id>.md` plus updates to the owning command/caller category files and both category directories.

Read [the shared contract](../../../workflows/source-documentation.md), [command detail template](../../../templates/command-detail.md), [command index template](../../../templates/command-index.md), [tool index template](../../../templates/tool-index.md), [tool category template](../../../templates/tool-category.md), [command category template](../../../templates/command-category.md).

Record source revision and date in affected pages. Do not add coverage or completion labels to indexes. Do not create `docs/scans/`, `log/`, or separate run reports.

Keep directories and category files compact: category navigation at the root and summary tables in category files. No Lifecycle/Implementation columns, detailed records, Historical bindings, or Notes. Link to real Markdown headings using the shared contract; never use custom HTML record anchors. Keep detailed explanations exclusively in requested doctify-cmd pages. Update both sides of relationships and category entry counts. Migrate old detailed indexes using the shared contract.

In each command document, put one short purpose sentence directly below the command title, without a **Purpose** section. Put **Structures used** after **Inputs and response** and before **Core logic flow**. Introduce the Rust types and sample values before explaining how the code uses them.

Match the readable layout in `docs/commands/layer/cmd-layer.new.layer.md` without copying its older **Purpose** heading or command-specific facts: in **Context to use**, state the prerequisite briefly, list distinct UI actions as short bullets with nearby evidence, and give headless behavior its own sentence when relevant. In **Inputs and response**, put a small invocation example in a fenced `json` block, group optional fields and defaults into short bullets, then state the result and error cases separately. Keep long source URLs out of dense prose by using concise link labels.

1. Accept an exact case-sensitive command ID (also handle the user's spelling doctify-cmds). Search both category tables and current source; resolve registration, aliases and shell routes. If absent, report it without substituting another ID. For catalog-only IDs, document missing implementation without fabricating logic.
2. Trace every material user flow reachable after invoking or choosing the command: caller/interception → admission/enabled checks → handler → important lower-layer algorithm → mutation/result/history. For tool-selection IDs, distinguish selecting the tool from using it; follow pointer down/move/up, click, keyboard gestures, modifier keys, alternate targets, preview/commit/cancel, lock and failure branches, and UI versus headless behavior. A direct toolbar choice may bypass the ID yet still activate the same tool behavior; document that relationship without claiming it dispatches the command. Do not stop at the ID handler when the command’s user-facing purpose depends on a later gesture.
3. Fill the command-detail template with the opening purpose sentence, Context to use, Inputs and response, Structures used, and Core logic flow. Do not add a standalone Purpose section. Explain every material phase and branch with enough simplified code to follow the real data flow. Create one level-three Core logic flow subsection per distinct user-visible flow, named by its trigger and result. Keep that flow’s press, movement, release, preview, commit, cancellation, and history together; use level-four phase headings within it when needed. Do not group independent flows beneath a generic phase heading. Show the dispatch boundary between flows, including any later gesture after tool selection. Trace preview construction and the eventual commit command rather than labeling a pointer-position update as the preview itself. Keep loops, conditions, parameter transformations, and state updates that determine the result. Remove boilerplate and incidental setup. Do not hide the algorithm behind invented helper names; if using explanatory pseudocode, label it explicitly. You may shorten, rename local variables, and combine branches for clarity; label every changed snippet "Adapted Rust" and never imply it is verbatim. Give each Rust code group a short purpose sentence before the code. Put explanations of a Rust code group's behavior in concise comments beside the relevant lines or branches, rather than in prose after the fence. Do not start code fences with generic Input, Response, or Explanation comments. At a call or branch whose return value is not obvious, add a nearby Rust comment with its actual return type and a plausible sample value; distinguish `Result<T, E>` from `T`, `Option<T>` from `T`, and final JSON from intermediate values. Omit obvious return comments. If a value is long, show only decisive fields or its type. Never imply an omitted error branch always succeeds. In Structures used, show compact Rust definitions or adapted Rust fragments for the actual types and fields involved; include concrete sample values in Rust comments to show what the structure holds during this command. Do not leave this section as a type-name list. Use a pinned GitHub blob URL with #Lstart-Lend (or #Lnumber) for the exact original source range; verify the lines at that revision. If GitHub location cannot be verified, use a local link with an explicit limitation. Prefer bullets and short sentences; avoid long prose. Do not add Effects, Tests and limits, or Revision history sections. Put any material failure, side effect, or limitation in the relevant flow, input, or context section. Explain relevant selection/layer/mask, color/depth, locks and ownership behavior.
4. Include a valid invocation example and prerequisites without executing a document mutation. Keep material effects and errors next to the phase that causes them. Do not add Tests and limits, Effects, Revision history, Historical bindings, or Notes sections.
5. Determine the command's category from the exact ID prefix before its first dot (`tools.defaultColors` → `tools`), not its menu or tool group. Create the matching `docs/commands/<prefix>/` folder and save the detail page there at its stable filename, with the exact command ID as its plain Markdown title. Do not create a second category index inside the folder. Search for a legacy page at the root or in another category folder; move it into the prefix folder, preserve its content, and update every local link to and from it. If the ID prefix changes later, move the page with the record. Derive the link fragment from the title (edit.undo → #editundo), not from the encoded filename.
6. Update the command-name cell and all corresponding command links in tool tables to this detail heading. Update verified reciprocal caller summaries within scope. Create missing tables without coverage labels. Link back from the detail page to category headings and directories. Do not insert detailed records or per-item headings into indexes.
7. Validate links to real headings, row identities, reciprocal relationships, source-line link accuracy, adapted-code labeling, concise comments and template completion. Report the detail page, changed tables and remaining gaps to the user. This is not a complete inventory scan.
