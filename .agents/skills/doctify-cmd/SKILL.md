# Explain one command from Rust source

Input: exact case-sensitive command ID and optional source checkout. If no ID was supplied, ask for it. Output: `docs/commands/<category-slug>/cmd-<encoded-id>.md` plus updates to the owning command/caller category files and both category directories.

Read [the shared contract](../../../workflows/source-documentation.md), [command detail template](../../../templates/command-detail.md), [command index template](../../../templates/command-index.md), [tool index template](../../../templates/tool-index.md), [tool category template](../../../templates/tool-category.md), [command category template](../../../templates/command-category.md).

Record source revision, date, coverage, and unresolved scope in affected pages. Do not create `docs/scans/`, `log/`, or separate run reports.

Keep directories and category files compact: category navigation at the root and summary tables in category files. No Lifecycle/Implementation columns, detailed records, Historical bindings, or Notes. Link to real Markdown headings using the shared contract; never use custom HTML record anchors. Keep detailed explanations exclusively in requested doctify-cmd pages. Update both sides of relationships and category entry counts. Migrate old detailed indexes using the shared contract.

1. Accept an exact case-sensitive command ID (also handle the user's spelling doctify-cmds). Search both category tables and current source; resolve registration, aliases and shell routes. If absent, report it without substituting another ID. For catalog-only IDs, document missing implementation without fabricating logic.
2. Trace caller/interception → admission/enabled checks → handler → important lower-layer algorithm → mutation/result/history. Include meaningful failure branches, async completion/cancel, preview versus commit and UI versus headless behavior.
3. Fill the command-detail template with Purpose, Context to use, Inputs/results, Core logic flow and Structures used. Explain every material phase and branch with enough simplified code to follow the real data flow. Keep loops, conditions, parameter transformations, and state updates that determine the result. Remove boilerplate and incidental setup. Do not hide the algorithm behind invented helper names; if using explanatory pseudocode, label it explicitly. You may shorten, rename local variables, and combine branches for clarity; label every changed snippet "Adapted Rust" and never imply it is verbatim. Give each Rust code group a short purpose sentence before the code. Do not start code fences with generic Input, Response, or Explanation comments. At a call or branch whose return value is not obvious, add a nearby Rust comment with its actual return type and a plausible sample value; distinguish `Result<T, E>` from `T`, `Option<T>` from `T`, and final JSON from intermediate values. Omit obvious return comments. If a value is long, show only decisive fields or its type. Never imply an omitted error branch always succeeds. In Structures used, show compact Rust definitions or adapted Rust fragments for the actual types and fields involved; include concrete sample values in Rust comments to show what the structure holds during this command. Do not leave this section as a type-name list. Use a pinned GitHub blob URL with #Lstart-Lend (or #Lnumber) for the exact original source range; verify the lines at that revision. If GitHub location cannot be verified, use a local link with an explicit limitation. Prefer bullets and short sentences; avoid long prose. Do not add Effects, Tests and limits, or Revision history sections. Put any material failure, side effect, or limitation in the relevant flow or context bullet. Explain relevant selection/layer/mask, color/depth, locks and ownership behavior.
4. Include a valid invocation example and prerequisites without executing a document mutation. Keep material effects and errors next to the phase that causes them. Do not add Tests and limits, Effects, Revision history, Historical bindings, or Notes sections.
5. Determine the command's owning category from `docs/commands/<category-slug>.md`. Create the matching `docs/commands/<category-slug>/` folder and save the detail page there at its stable filename, with the exact command ID as its plain Markdown title. Do not create a second category index inside the folder. Search for a legacy page at `docs/commands/cmd-<encoded-id>.md`; move it into the category folder, preserve its content, and update every local link to and from it. If the category changes later, move the page with the record. Derive the link fragment from the title (edit.undo → #editundo), not from the encoded filename.
6. Update the command-name cell and all corresponding command links in tool tables to this detail heading. Update verified reciprocal caller summaries within scope. Create missing tables with partial coverage. Link back from the detail page to category headings and directories. Do not insert detailed records or per-item headings into indexes.
7. Validate links to real headings, row identities, reciprocal relationships, source-line link accuracy, adapted-code labeling, concise comments and template completion. Report the detail page, changed tables and remaining gaps to the user. This is not a complete inventory scan.
